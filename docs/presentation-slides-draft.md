### Слайд 2 — Актуальность

- Рост числа обращений в автосервисы при нехватке квалифицированных приёмщиков в часы пик.
- Клиенты ожидают быстрый ответ онлайн; задержка снижает конверсию в запись.
- Разрозненные каналы (телефон, мессенджеры, CRM) не дают единого стандарта сбора данных о ТС и симптомах.
- Локальные языковые модели позволяют автоматизировать первичный диалог **без передачи данных во внешнее облако**.

**Рисунок:** без обязательного рисунка или общее фото/иконка СТО (не из текста ВКР).

### Слайд 3 — Проблема существующего процесса

- Высокая нагрузка на персонал в часы пик; параллельная обработка нескольких обращений увеличивает риск ошибок.
- Нет единого стандарта уточняющих вопросов — данные обращений неоднородны по полноте.
- Качество консультации сильно зависит от опыта и состояния конкретного сотрудника.
- Информация разрозненно хранится (CRM, мессенджеры, таблицы) — сложно анализировать поток обращений.

**Рисунок:** без обязательного рисунка (можно позже упростить до блок-схемы «AS-IS» как на следующем слайде).

### Слайд 4 — Цель работы и задачи *(из задания на ВКР)*

**Цель (практический результат):** автоматизировать первичную консультацию клиента автосервиса: интеллектуальный анализ обращения, предварительная стоимость услуг в формате «от», формирование и передача заявки на обслуживание.

**Задачи:**

1. Проанализировать предметную область автосервиса и проблемы первичной консультации.

3. Спроектировать архитектуру интеллектуальной системы и модель БД.
4. Реализовать локальный ИИ-ассистент для анализа обращений.
5. Разработать клиентскую и серверную части веб-приложения; реализовать передачу заявки.
6. Провести тестирование системы.

### Слайд 6 — Пользователи и роли системы

- **Клиент** — ввод описания проблемы бытовым языком; нужна быстрая предварительная информация и удобный веб-доступ.
- **Менеджер (администратор приёма)** — получает уже структурированную заявку и результат первичного анализа.
- **Руководство** — интерес к сокращению времени обработки обращений и накоплению аналитики по типам обращений.
- **Администратор системы** — роли пользователей, сценарии консультации, контроль работы ИИ-модуля, безопасность.

**Рисунок:** при желании простая схема «роли ↔ интерфейс» своими блоками или без иллюстрации.

### Слайд 7 — Бизнес-процесс: AS-IS и TO-BE

- **AS-IS:** клиент обращается по разным каналам → менеджер вручную уточняет данные → фиксация в CRM или вручную → заявка специалистам; мало регламента, субъективная оценка стоимости.
- **TO-BE:** клиент ведёт диалог в веб-интерфейсе → сервер и ИИ анализируют текст, при нехватке данных задают уточняющие вопросы → классификация, предварительные рекомендации, стоимость «от», confidence → структурированная заявка менеджеру (в т.ч. уведомление).

**Рисунок:** [`thesis/images/media/image1.jpg`](thesis/images/media/image1.jpg) — BPMN текущего процесса (AS-IS) из пояснительной записки.

### Слайд 8 — Взаимодействие компонентов (процесс консультации)

- Клиент инициирует сессию через веб-интерфейс; сообщения сохраняются на сервере.
- Текст передаётся в модуль ИИ; возвращаются гипотезы, список недостающих данных и показатель **confidence**.
- Вариант с недостаточными данными: уточняющий вопрос пользователю; при достаточных — расчёт ориентировочной стоимости и отображение результата.
- После подтверждения создаётся заявка в БД; возможно уведомление менеджера (в работе — интеграция с Telegram-ботом).

### Слайд 9 — Аналоги и отличие разрабатываемой системы

- **CRM** — учёт клиентов и заявок, но без интеллектуального разбора свободного текста обращения.
- **Онлайн-формы** — частичная структура полей, без адаптивного диалога при нехватке данных.
- **Сценарные чат-боты** — жёсткие ветки, слабая работа со свободным описанием симптомов.
- **Отличие:** анализ текста в свободной форме, извлечение параметров автомобиля и симптомов, уточняющие вопросы, классификация по услугам, **confidence**, стоимость «от», автоматическое создание заявки для менеджера.

**Рисунок:** по желанию — один столбец «аналоги / наша система» текстом, без отдельного файла.

### Слайд 10 — Требования к системе

**Функциональные (фрагмент):**

- Анализ обращения (NLP/LLM), извлечение структурированных параметров ТС и симптомов.
- Вероятностные гипотезы неисправностей, расчёт **confidence**, рекомендуемый вид услуги.
- Ориентировочная стоимость «от» по справочнику; сохранение истории консультации; создание заявки для менеджера.

**Нефункциональные (фрагмент):**

- Локальное развёртывание ИИ-модуля (без обязательной зависимости от платных внешних API).
- Конфиденциальность данных; работа в браузере на ПК и мобильных устройствах (адаптивный UI).
- Масштабируемость серверной части; устойчивость к ошибочному вводу; прозрачность для пользователя (предварительный характер выводов).

**Рисунок:** нет.

### Слайд 11 — Архитектура решения

- Клиент — адаптивное веб-приложение (в т.ч. в концепции PWA): только UI и вызовы API, без локального ИИ в браузере.
- Сервер — Node.js: REST API, сессии консультаций, доступ к БД, интеграция с ИИ-модулем.
- Подсистема ИИ — локальная LLM (**Qwen 2.5** через **Ollama**).
- Хранение — **PostgreSQL**; передача заявки менеджеру после завершения сессии.

### Слайд 16 — Подсистема искусственного интеллекта

- Взаимодействие с моделью по HTTP API **Ollama**; запрос с историей сообщений сессии; ответ в JSON.
- **Гибридный алгоритм:** предварительный rule-based анализ симптомов + вывод LLM; при ошибках/пустых данных — устойчивый fallback.
- Ответ модели жёстко структурируется схемой (гипотезы, рекомендуемые проверки, срочность, **confidence**, **estimated_cost_from**, краткое резюме).
- Локальная модель: автономность, контроль над данными, снижение риска утечки по сравнению с облачным API.

**Рисунок (схема для вёрстки):**

```
Клиент → Express (consultations) → preAnalyzeSymptoms (rules)
              ↓
         Ollama /api/chat (JSON schema)
              ↓
         mergeDiagnosis → UI + заявка менеджеру
```
